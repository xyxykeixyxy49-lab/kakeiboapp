# LINE構成デザイナーをMCPで操作する

公式LINEの構成図を作るWebアプリ「LINE構成デザイナー」(https://linevisual.vercel.app)を、
Claudeから「LINE構成デザイナー」コネクタで操作するときの手順です。
データはアプリと同じNotionに保存されるので、ここでの変更はそのままアプリの構成図・トーク風プレビューに出ます。

## はじめに:ツールがあるか確認する

`list_projects` などのツールが見当たらないときは、作業を始めずにこう伝える:
「claude.ai の『設定 → コネクタ』で LINE構成デザイナー を追加し、会話の『＋(ツール)』でオンにしてください。
接続用のURLはアプリの『🤖 Claude連携』(https://linevisual.vercel.app/setup/mcp)で確認できます。」

## 基本の流れ

1. **探す**:`list_projects` で案件を確認する(案件名の一部でも指定できる)。
2. **今の構成を読む**:`get_flow` で全体を読んでから編集する。ノード名・ボタン名・つながりを把握しないまま足すと、重複や迷子のノードができる。
3. **大きな変更は先に一言**:ノードを5個以上足す・消すときは、作る流れを箇条書きで短く示してから作る(小さな修正ならそのまま実行してよい)。
4. **編集する**(下の「ツールの使い分け」)。
5. **整える**:ノードを3個以上足したら最後に `auto_layout`。
6. **確かめる**:最後に `get_flow` をもう一度読み、意図どおりにつながっているか・「(未接続)」のボタンが残っていないか・本文がおかしくないかを確認する。見つけたら直してから報告する。
7. **報告する**(下の「報告のしかた」)。

## ツールの使い分け

| やりたいこと | ツール | ポイント |
|---|---|---|
| 案件を作る | `create_project` | 起点ノード「友だち追加」が自動でできる。tool は lstep / lmessage |
| 使える部品を知る | `list_node_kinds` | Lステップ/Lメッセージで呼び名が違う。kind はここで確認する |
| 次のノードを足す | `add_node` + `after` | `after_button` を省略すると「次へ(続けて送る)」からつながる |
| ボタンの先にノードを足す | `add_node` + `after` + `after_button` | まだないボタン名を書くと、ボタンも作ってからつなぐ |
| 選択肢と分岐先を一度に足す | `add_branch` | テキストに使うとボタン付きメッセージに変わる |
| ボタンをまとめて設定 | `set_buttons` | 各ボタンに `target` を書けば一度で全部つながる |
| カルーセルのカード | `add_node` の `cards`、または `set_cards` | カードのボタンのつなぎ先は `set_cards` の `target` で |
| つなぎ替え・外す | `connect` | `to: null` で外す |
| 文言・名前・メモの修正 | `update_node` | 指定した項目だけ変わる |
| 画像を付ける | `set_image` | `card` を指定するとカードの画像に |
| 削除 | `delete_node` | 消す前にユーザーに確認する(他のノードからのつながりも外れる) |
| 並べ直す | `auto_layout` | |

ノードは名前でもIDでも指定できる。同じ名前が複数あるとエラーで候補が返るので、そのときはIDを使う。

## 失敗しやすい点(ここが大事)

- **同じノードを変える操作を同時に送らない。** 各ツールは「読み込み → 変更 → 保存」をノード単位で行うため、
  同じノード(例:同じボタンノードの別々のボタンに `add_node` で子をつなぐ、同じカルーセルの別カードに `set_image`)を
  並列で呼ぶと、後から保存した方が先の変更を上書きする。同じノードに触る操作は1つずつ順番に。
  別々のノードを触る操作(独立した `update_node` など)は並列でよい。
- **改行は本物の改行で書く。** 本文に「\n」と2文字で書かず、実際に改行した文字列を渡す
  (サーバー側でも直すが、表示崩れを防ぐため最初から正しく)。
- **クイックリプライ・ボタンは全部つなぐ。** ヒアリングの選択肢が全部同じ次の質問へ進む場合も、
  `set_buttons` で各ボタンに同じ `target` を設定する。つながっていないボタンはプレビューで「遷移先が未設定」になる。
- **起点(trigger)へはつなげない。** 「最初に戻る」ような動きは、起点の次のノード(あいさつ等)につなぐ。
- **ボタン数の目安**:ボタン 4 個 / クイックリプライ 13 個 / リッチメニュー 6 枠 / カルーセル 10 枚。超えるときは分けるか、ユーザーに相談する。
- **ホームページ等へのリンク**は `action` ノードにまとめ、名前を「HP:〇〇」、本文を「URLを開く:https://…」にする。
  リッチメニューやカードのボタンから、そのノードにつなぐ。
- **仮の値**(〇〇駅、0120-000-000、example.com など)を使ったら、そのノードの `memo` に「実際の〇〇に差し替えてください」と残す。
- **画像を新しく作る・探すのは、確認してから。** AI画像生成(Canva等)はユーザーの利用回数を消費する。
  `set_image` に渡せるのは https:// の画像URLか、アプリ同梱の `/samples/…` だけ。

## 新しく構成を組むときの型

業種を問わず、次の骨組みから考えると抜けが少ない。

1. **起点**(流入経路):どこから友だち追加されるか(QR・HP・広告)。メモに計測の工夫を書くと親切。
2. **あいさつ**:お礼+何ができるか+「1分の質問にお答えください」。
3. **ヒアリング**(ボタン):目的・関心で分岐 → 各分岐の最初に **タグ付け**。
4. **分岐ごとの中身**:クイックリプライで条件を順に聞く → **アクション**で回答を保存 → おすすめ(カルーセル)→ 申込フォーム。
5. **申込のあと**:タグ → 担当者へ通知(アクション)→ 受付完了 → **待ち時間** → 前日リマインド。
6. **すぐ決めない人向け**:お役立ち配信の案内 → 待ち時間 → コラムのカルーセル(最後のカードに「相談する」)。
7. **相談窓口**(ボタン):チャット/電話/来店・オンライン予約。
8. **リッチメニュー**(最大6枠):よく使う入口(探す・予約・相談・条件登録・会社案内など)をまとめ、それぞれ該当ノードへ。

本文は実際に配信できる自然な日本語で書く(絵文字は1メッセージに1〜2個まで)。
フォームの本文は質問項目を1行に1つ。各ノードの `memo` には、お客様と打ち合わせで話せる運用のコツを一言入れると喜ばれる。

## 報告のしかた

ユーザーは非エンジニアのことが多い。次の順で、日本語で短く伝える。

1. 何をしたか(案件名、作った・変えたノードの数)
2. 流れの要約(分岐ごとに1行。表にしてよい)
3. 差し替えが必要な仮の値(URL・電話番号など)
4. 「アプリを開いている場合は再読み込みすると反映されます」
5. 次にできること(画像を入れる、プレゼンモードで見せる など)を1〜2個

うまくいかなかった操作があれば、隠さずに何が残っているかを書く。
